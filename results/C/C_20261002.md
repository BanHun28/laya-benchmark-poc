## Anomalies / notes
- Verbatim warnings: none. The probe's `run_card.warnings` is `[]`, and the 9 laya-evals logs have no Warning either (multilingual does not raise the temperature clamp warning). stderr held only Hub cache-check progress bars like `Fetching 5 files: 100%|██████████| 5/5 [00:00<00:00, 1526.76it/s]`.
- v2c does not fit the default head budget. Its option tokens total 418, over the limit of 240 (=256−16), and laya truncates every option to 30 tokens (laya/common.py `build_head`). So most of the examples and smart_home's "(오디오 재생·음량은 제외)" (excluding audio playback and volume) are invisible to the model (decoded option text in BUILD.md). The requested v2c was measured with laya-evals as is. To see the effect of the example content, a v2c_h512 diagnostic run was added, but even at 512 the tokenizer's cap of 48 tokens per option truncates the smart_home examples and the second productivity example. v2c_h512 was run not through the CLI but with `laya.evals.evaluate`, fed the same torch Router as the CLI, through a runner that attaches a per-request `head_max_len`.
- v2a also nearly fills the head budget (234/240). If the next wording round lengthens the descriptions further, every option will be truncated, as with v2c.
- The v2c examples were replaced 2 times (before the model runs). The first info_qa example '오늘 서울 날씨 어때' contained the dev utterance '서울' (row 340, transport) as a substring, so it was replaced. Its replacement '이번 주말 날씨 알려줘' shared '알려줘' with a lifestyle example, so it was changed again, to '이번 주말 날씨 어때'. None of the final 16 examples exactly matches a dev state, and none contains one as a substring. Across all 500 rows of the file there are also 0 exact matches.
- The `_general` reports of v2b and v2e have choice_accuracy 0.000 by construction, because the gold option is not in the schema. They are used only for the gate analysis.
- The media, smart_home and info_qa descriptions of v2e reuse the v2a wording as is, and the option order is the order listed in the task instructions (assistant_tasks, media, smart_home, info_qa, daily_life) (assumption). The other 6 options of v2d keep the relative order of v2a (assumption).
- The C1 permutations were generated per file by consuming one `random.Random(13)` in dev item order (permutations 1\~5 of item 1, then item 2's …). There are 0 identity permutations. All orders are stored in the JSON.
- Shared machine: other heavy processes ran on the same machine, and `scripts/calibrate_ko.py`, apparently Track E work, appeared at 17:33. Accuracy is unaffected, being on the deterministic CPU fp32 path. The latency column of the reports is not interpreted. Power was AC.
- `results/C/__pycache__` and `scripts/__pycache__/probe_option_order.cpython-312.pyc`, created by the compile check, were deleted.

## Next actions
- **G4 not met.** Under the 00 §6 verdict rules this is a Conditional Go (operational guard) case. Guard candidates: (a) fixing the option order in production (already in 05 §4) (b) a confidence gate. The flip of decisions with answer_confidence ≥ 0.9 is 0.094, close to the G4 level. Whether to redefine G4 as "flip of decisions that pass the gate" is for the project owner to decide. With the current wording it is not met.
- **router_v2: none adopted, router_v1 kept.** Round 2 of 05 P1 step 7 (at most 2 rounds) is optional. Judging by these results, wording is unlikely to close the G1 gap (dev 0.560 → 0.80). This serves as evidence for the ADR to enter P4 (fine-tuning). If coarse routing is acceptable, a policy layer that sums v1 probabilities per class is better than schema v2e (0.682 vs 0.536 on the same 220 rows). But this changes the task contract, so it is an owner decision.
- Keep the general option. Removing it and replacing it with a gate turns general rows into confident wrong answers on smart_home (§3).
