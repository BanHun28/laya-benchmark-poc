- A의 phase: prepare_model 0.0 s, prepare_items 0.0 s(legacy cache; 실제 전처리는 어댑터가 7.4 s), setup(config·tokenizer·build+load·items·optimizer) 2.4 s, train loop 699.3 s, epoch checkpoint 저장 1.4 s, calibration(100행 forward + LBFGS 0.03 s) 13.4 s, export 1.2 s, `train()` 합계 717.8 s, 프로세스 wall 721.4 s. `laya.load("poc/finetune/ckpt_probe", device="cpu")` 4.2-5.5 s, 정상 로드.
- optimizer step 오버헤드(AdamW 322M params + clip): 경합 하 1.5-1.8 s/step.
- 첫 shape(MPS 커널 컴파일) 비용은 전체의 1% 남짓이라 추정에 영향 없음. full train set의 seq_len은 207-266(45종)뿐이다.
- gradient checkpointing은 이 길이(≤266 토큰)에서 메모리를 조금만 아낀다. mb2는 allocated 차이가 샘플링 오차 수준이고 driver가 0.45 GB 줄며, mb8은 allocated가 2.3 GB 준다. 반면 mb2에서 1.2배, mb8에서 1.49배 느리다. MPS 메모리는 1 Hz 샘플이라 순간 peak는 놓칠 수 있고, RSS max는 `ru_maxrss`라 정확하다. 메모리는 가중치·grad·AdamW 상태(약 5.2 GB, 임베딩 256k×768이 파라미터의 61%)가 지배한다.
- loss: 스크립트 로그(micro-batch 하나의 값이고 RL 항 때문에 음수가 될 수 있음) step 100 0.554, 200 2.125, 300 4.241, 400 0.024, 500 −0.514, epoch 평균 1.187. runner가 같은 logits로 잰 CE(100 item 창 10개): 1.43, 1.59, 1.34, 1.12, 1.00, 1.36, 1.21, 0.94, 1.14, 1.28. train acc 0.61 → 0.71-0.79.
- 검증: runner가 collate에 들어온 item의 출처를 셌다. 학습 단계는 train 1,000개뿐이고 calibration 단계는 validation 100개뿐이다(B-D도 같은 결과).

**머신 부하.** 브리프에 적힌 같은 머신의 다른 작업 부하(\~30% CPU)와 실제가 달랐다. 시작 시점 그 작업(Llama-3.1-8B)은 CPU 11%, footprint 24 GB, GPU "Device Utilization %" 99-100%였다. 19:46-19:56 사이에 끝났고, 같은 작업 큐가 다른 작업 2개(Qwen2.5-7B 포함)를 동시에 돌렸다. 프로브 내내 GPU utilization 중앙값은 100%였다(A의 71개 샘플 중 최소 21%). MPS fp32 matmul 기준치는 3.4-4.1 TFLOPS, 시스템 CPU 중앙값은 21%, 사용 메모리는 26-29 GB/48 GB였다. A의 micro-batch 500개 중 98개는 경합이 잠깐 풀린 구간에서 0.14-0.35 s(중앙값 0.30 s)로 끝났다. 따라서 위 시간은 경합으로 3-5배 부풀려진 값으로 읽는다.

## 이상 / 주석

- 경고: 학습·평가 로그에 warning·fallback·clamp 메시지 없음. 정보 줄만 있다. 스크립트 "Using legacy cached training items without metadata: poc/finetune/data/items_probe.pt"(의도한 경로), datasets "Using the latest cached version of the dataset since mteb/amazon_massive_intent couldn't be found on the Hugging Face Hub (offline mode is enabled)."(rows 단계).
- base 체크포인트 불변: `tokenizer/tokenizer_config.json`과 `rl_agent_config.json` sha256이 전후 같고 symlink도 유지됐다. `_fix_tokenizer_config`는 이 snapshot에서 no-op이다(이미 dict 형 `extra_special_tokens`).
- upstream 스크립트 무수정(sha256 22ffb2bea0bb24a4…). runner는 모듈 함수(print, collate, build_model, save_checkpoint, fit_temperature, prepare_*, train)만 감싸고 torch seed를 준다.
- 내보낸 `rl_agent_config.json`: `model_name`이 "laya-typed-decisions"로 하드코딩돼 있다. base의 `training` 블록(updates 15987, epochs_completed 4, hours 4.97)이 그대로 남아 출처를 오해하게 만든다. `max_tokens_per_batch` 2048과 `gradient_checkpointing` true가 추가된다. Agent는 이 키들을 읽지 않으므로 추론에는 영향이 없다.
- test half 사용: 브리프대로 probe 체크포인트로 domain_8 test half를 채점했다. 05 §6 P1.3의 "동결 버전마다 1회" 원칙에 따라 full run의 하이퍼파라미터(epoch, 배치)는 dev 수치로만 고른다. 이 run의 test 수치는 파이프라인 확인용이다.
- dev 2,012의 base 0.462가 500행 0.526보다 낮은 이유: 500행은 도메인 균등 층화이고 dev는 자연 분포(productivity 26%, info_qa 21%)인데, base가 이 두 도메인에 약하다.
- 프로브 학습셋은 도메인 균등(125×8)이다. full run은 자연 분포(productivity 2,917 \~ transport 557)라 prior가 달라진다.

## 문서 불일치 (docs 미수정, 보고만)

1. 05 §6 P4 "빌더 `massive --lang ko --mode domain --split train`": 빌더에 `--split` 플래그가 없다. `MASSIVE["split"]`이 "test"로 고정돼 있어(build_ko_evalsets.py:41-42) 그 함수와 상수를 import해 썼다.
2. 05 §6 P4 "산출 체크포인트는 `laya.load(output_dir)`로 로드해 P1과 같은 명령으로 재평가": `laya-evals run --model <디렉터리>`는 `ValueError: unknown model 'poc/finetune/ckpt_probe'; choose one of ['english', 'multilingual', 'typed-decisions'] ...`로 실패한다(Router 이름만 받음, router.py:112-118). 그래서 wrapper로 평가했고, base 재현은 0 flip이다.
3. 05 §6 P4 "dev half는 early-stopping/calibration용": 스크립트에는 early stopping이 없다. 고정 epoch에 매 epoch `checkpoint_latest/`를 덮어쓴다. calibration slice도 items 파일 안에서 위치로 뽑는다(seed 20260922, min(--calib-max, N//10)). 어댑터가 validation 행을 그 위치에 놓고, runner의 `--keep-epoch-checkpoints`가 epoch별 사본을 남겨 dev 기반 선택을 가능하게 한다.
4. 05 §6 P4 인자 목록에 `--force-preprocess`, `--model-id`가 빠져 있다. `--force-preprocess`(또는 다른 키의 `<items>.meta.json`)는 우리 items 파일 위에 LocalLLaMA/typed-decisions를 다시 받아 덮어쓴다. 절대 쓰지 않는다.
5. README "Fine-tune for better accuracy"(README.md:91): MPS 스크립트도 "build dataset, train with RLCD, calibrate temperatures, evaluate, export"를 한다고 적혀 있지만, MPS 스크립트에는 evaluate 단계가 없다.
6. docs/finetune.md(upstream 클론, 공개 저장소에는 포함하지 않음) §Calibration "1.0 for a slice under ten items, 1.2 if the fit raises": Kaggle 노트북에는 맞다(try/except). MPS 스크립트는 1.2를 샘플 0개 type에만 쓰고 try/except가 없어, fit이 실패하면 최종 export 전에 중단된다. `checkpoint_latest`만 남는다.
7. docs/finetune.md knobs 표(fp16 autocast, effective batch 64, `max_tokens_per_batch` 4096)는 Kaggle 노트북 값이다. MPS 스크립트는 fp32, effective batch 32(2×16), `max_tokens_per_batch` 2048(config에만 기록되고 루프는 쓰지 않음)이고, README의 MPS 설명은 이 차이를 말하지 않는다.
8. 05 §1·§6의 "MASSIVE ko train 11,514행"은 원본 수다. 빌더와 같은 필터를 거치면 11,094행이다.
9. 05 열린 질문 13(gold 형식): 해소. choice gold는 `{"probabilities": {<criteria key>: p}}`로 key 기반이다(index 아님). 우리 `expected` 문자열은 `{"probabilities": {key: 1.0}}`로 1:1 매핑된다.

- **옵션 순서 셔플 증강(결정 사항, train만).** `make_domain8_items.py items --shuffle-options {none,all}`, 기본 `all`. train 행 i의 criteria key 순서를 `random.Random(13 + i)`로 섞은 dict를 `build_training_item`에 넘긴다. key→설명과 gold key는 그대로이고 target·label이 순열을 따른다. validation(calibration 400행)은 canonical 순서다. 선택은 `poc/finetune/data/items_full.provenance.json`(`shuffle_options`, `option_order`, `options_reordered`, `gold_slot`, `decoded_example`)과 `poc/finetune/READY`에 기록했다. 프로브 items는 셔플 없이 만들었으므로 `run_probe.sh`에 `--shuffle-options none`을 고정했다.

- **검증.** 빌드가 모든 아이템을 tokenizer로 decode해 assert한다. 각 옵션 텍스트가 `<key>: <설명>`이고, target의 gold slot이 gold key이며, 앞 20개는 같은 순서의 inference 시퀀스와 같다. 재배열은 train 11,093/11,094이다(항등 순열 1행 `train:1625`, 기댓값 11,094/8! ≈ 0.28). validation은 0/400이다. gold slot 분포는 1,342–1,431로, canonical의 slot 0 = productivity 2,917 … slot 6 = transport 557 쏠림이 사라졌다. 신·구 파일을 쌍으로 대조했다. 길이·head·state 토큰이 같고, 옵션 span 집합이 같으며, gold span이 label 위치에 있다. 스크립트 hold-out(`Random(20260922)`)의 calibration slot 400개는 모두 validation 행이고 구 파일과 동일하다. `--shuffle-options none`은 구 파일을 바이트 단위로 재현한다(같은 파일명일 때. torch.save가 zip 폴더 이름을 파일명에서 딴다).
