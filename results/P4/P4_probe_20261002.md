**Machine load.** The load of the other job on the same machine stated in the brief (\~30% CPU) differed from reality. It ended between 19:46-19:56, and the same job queue then ran 2 other jobs (including Qwen2.5-7B) concurrently. Throughout the probe the median GPU utilization was 100% (minimum 21% over the 71 samples of A). The MPS fp32 matmul baseline was 3.4-4.1 TFLOPS, the median system CPU 21%, and memory in use 26-29 GB/48 GB. 98 of A's 500 micro-batches finished in 0.14-0.35 s (median 0.30 s) in windows where the contention briefly eased. So read the times above as inflated 3-5× by contention.

## Anomalies / notes

- Warnings: no warning, fallback or clamp messages in the training and evaluation logs. Only info lines: the script's "Using legacy cached training items without metadata: poc/finetune/data/items_probe.pt" (the intended path) and datasets' "Using the latest cached version of the dataset since mteb/amazon_massive_intent couldn't be found on the Hugging Face Hub (offline mode is enabled)." (rows step).
- Base checkpoint unchanged: the sha256 of `tokenizer/tokenizer_config.json` and `rl_agent_config.json` are the same before and after, and the symlinks were kept. `_fix_tokenizer_config` is a no-op on this snapshot (`extra_special_tokens` is already a dict).
- The upstream script is unmodified (sha256 22ffb2bea0bb24a4…). The runner only wraps module functions (print, collate, build_model, save_checkpoint, fit_temperature, prepare_*, train) and sets the torch seed.
- The exported `rl_agent_config.json`: `model_name` is hardcoded to "laya-typed-decisions". The base's `training` block (updates 15987, epochs_completed 4, hours 4.97) is left as is, which misleads about provenance. `max_tokens_per_batch` 2048 and `gradient_checkpointing` true are added. Agent does not read these keys, so inference is unaffected.
- Use of the test half: per the brief, the domain_8 test half was scored with the probe checkpoint. Following the "1 time per frozen version" principle of 05 §6 P1.3, the full-run hyperparameters (epochs, batch) are chosen from dev figures only. The test figures of this run are for pipeline verification.
- Why base 0.462 on dev 2,012 is lower than 0.526 on the 500 rows: the 500 rows are stratified evenly across domains, whereas dev has the natural distribution (productivity 26%, info_qa 21%), and base is weak on these two domains.
- The probe training set is domain-balanced (125×8). The full run uses the natural distribution (productivity 2,917 \~ transport 557), so the prior changes.

## Doc inconsistencies (docs not modified, reported only)

1. 05 §6 P4 "builder `massive --lang ko --mode domain --split train`": the builder has no `--split` flag. `MASSIVE["split"]` is fixed to "test" (build_ko_evalsets.py:41-42), so its function and constants were imported and used.
2. 05 §6 P4 "load the output checkpoint with `laya.load(output_dir)` and re-evaluate with the same command as P1": `laya-evals run --model <directory>` fails with `ValueError: unknown model 'poc/finetune/ckpt_probe'; choose one of ['english', 'multilingual', 'typed-decisions'] ...` (it accepts only Router names, router.py:112-118). So the evaluation used the wrapper, and the base reproduction has 0 flips.
3. 05 §6 P4 "the dev half is for early-stopping/calibration": the script has no early stopping. With a fixed number of epochs it overwrites `checkpoint_latest/` every epoch. The calibration slice is also taken by position inside the items file (seed 20260922, min(--calib-max, N//10)). The adapter places the validation rows at those positions, and the runner's `--keep-epoch-checkpoints` keeps a copy per epoch, which makes dev-based selection possible.
4. The argument list of 05 §6 P4 lacks `--force-preprocess` and `--model-id`. `--force-preprocess` (or a `<items>.meta.json` with a different key) re-downloads LocalLLaMA/typed-decisions over our items file. Never use it.
5. README "Fine-tune for better accuracy" (README.md:91): it says the MPS script also does "build dataset, train with RLCD, calibrate temperatures, evaluate, export", but the MPS script has no evaluate step.
6. docs/finetune.md (upstream clone, not included in the public repository) §Calibration "1.0 for a slice under ten items, 1.2 if the fit raises": correct for the Kaggle notebook (try/except). The MPS script uses 1.2 only for types with 0 samples and has no try/except, so if the fit fails it aborts before the final export. Only `checkpoint_latest` remains.
7. The knobs table of docs/finetune.md (fp16 autocast, effective batch 64, `max_tokens_per_batch` 4096) has the Kaggle notebook values. The MPS script uses fp32, effective batch 32 (2×16) and `max_tokens_per_batch` 2048 (recorded only in the config; the loop does not use it), and the README's MPS description does not mention these differences.
8. "MASSIVE ko train 11,514 rows" in 05 §1·§6 is the original count. After the same filters as the builder it is 11,094 rows.
9. 05 open question 13 (gold format): resolved. The choice gold is key-based, `{"probabilities": {<criteria key>: p}}` (not an index). Our `expected` strings map 1:1 to `{"probabilities": {key: 1.0}}`.

## Addendum 2026-10-03: full run preparation finalized (main training run not run)

- **Option-order shuffle augmentation (decided; train only).** `make_domain8_items.py items --shuffle-options {none,all}`, default `all`. For train row i, a dict with the criteria key order shuffled by `random.Random(13 + i)` is passed to `build_training_item`. The key→description mapping and the gold key are unchanged; target and label follow the permutation. validation (the 400 calibration rows) is in canonical order. The choice is recorded in `poc/finetune/data/items_full.provenance.json` (`shuffle_options`, `option_order`, `options_reordered`, `gold_slot`, `decoded_example`) and in `poc/finetune/READY`. The probe items were built without shuffling, so `--shuffle-options none` is pinned in `run_probe.sh`.
- **items replaced.** `items_full.pt` sha256 0ec55377920468d7… (11,094 + 400, seq_len 207–266, same size). The previous canonical build was only renamed, to `items_full_noshuffle.pt` (sha256 7a0f03361e0f9fc6…, bytes unchanged).
- **Verification.** The build decodes every item with the tokenizer and asserts: each option text is `<key>: <description>`, the gold slot of the target is the gold key, and the first 20 equal the inference sequence in the same order. Reordered: train 11,093/11,094 (1 row with the identity permutation, `train:1625`; expected count 11,094/8! ≈ 0.28). validation 0/400. The gold slot distribution is 1,342–1,431, so the canonical skew of slot 0 = productivity 2,917 … slot 6 = transport 557 is gone. The new and old files were compared pairwise: lengths, head and state tokens are the same, the sets of option spans are the same, and the gold span is at the label position. The 400 calibration slots of the script hold-out (`Random(20260922)`) are all validation rows and identical to the old file. `--shuffle-options none` reproduces the old file byte for byte (with the same file name; torch.save takes the zip folder name from the file name).
- **Evaluation changes.** `eval_ckpt.py overlap` reports accuracy including/excluding train-overlap rows, by exact state (utterance) match, together with n. The dev/test halves are reported only for the 500 rows that `results/B/B_splits.json` defines for the same file; the 2,917 rows and dev-2012 get only all. Overlaps: 33 in the 500 rows (dev 17, test 16), 155 in the 2,917 rows, 116 in dev-2012. Class distributions are not resampled. The new `eval_ckpt.py epochs` compares the epoch copies and the final export on dev-2012 with exact McNemar. Rule: v1 is the final export, and an epoch is reported as a v1 candidate only if it is more accurate on dev with p < 0.05 (no automatic replacement; the epoch copies carry the base temperature).
- **`run_full.sh` rewritten.** It is non-interactive. A preflight checks the inputs, 6 GB of disk and the items sha256 in READY, and claims the output directory with `mkdir`. Each step writes `STEP <name> OK|FAILED` to `results/P4/full_run_status.log`, and the last line is `RUN_FULL FINISHED|FAILED` (exit ≠ 0 on failure). Logs and reports go to `results/P4/full_<YYYYmmdd-HHMM>_*`, metrics to `results/P4/metrics/full_<ts>_*`. intent_20opt and the full YNAT 500 were removed from the evaluation list (per the 05 §6 P4 evaluation list; YNAT is dev 245).
- **smoke.** `SMOKE=1 bash poc/finetune/run_full.sh` runs 64 train rows × 1 epoch with mb8, with output in `results/P4/smoke_full/`. The final script run `smoke_20261003-1148` had all 14 STEPs OK, `RUN_FULL FINISHED`, in 6 min 33 s (training 11 s, evaluation 6.3 min, checkpoints deleted). The flip-probe parity is 250/250. Two independent smokes gave the same values, dev 0.5696 and flip 0.261.
