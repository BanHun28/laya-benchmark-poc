**배포 함의(PoC).**

- multilingual 단일 한국어 문의 1\~3문항은 in-process MPS 14\~23 ms, CPU 34\~57 ms다. HTTP를 거쳐도 MPS 3q 10 RPS p95가 79 ms다.
- MPS 이점은 2\~3배에 그친다. 트래픽이 간헐적이면 idle 페널티 때문에 1.2\~2배로 더 줄어든다(D1c, D6 open-loop).
- 서버는 추론을 직렬화한다. 처리량 상한은 1 / 서비스 시간으로, MPS 3q 약 22 RPS, CPU 3q 약 10 RPS다.
- CPU에서 혼합 길이 배치는 `sort_by_length=True`가 필수다. 정렬 없이 묶으면 loop보다 느리다.
- 이 머신에서 ONNX(fp32·int8)는 torch CPU보다 느리고, int8은 결정의 7%를 바꾼다.

## 3. D3 cold load

`results/D/20261003-1306_coldload.{json,md}`. 측정마다 새 프로세스에서 `import laya` → `laya.load(local path)` → 첫 `predict(short, 3q)` 순으로 잰다. 체크포인트 3종 × {cpu, mps} × 3회다. TTFA는 스크립트 시작부터 첫 답까지이고 인터프리터 기동은 뺐다. process wall은 부모가 잰 spawn부터 종료까지다. tokenizer 시간은 첫 답 뒤 같은 프로세스에서 `AutoTokenizer.from_pretrained`를 다시 실행해 쟀다(파일 캐시 warm).

- torch 행의 정확도와 ECE는 Track B 리포트 `results/B/20261002-1645_multilingual_ko_klue_ynat_7.json`과 같다(0.634, 0.1723). fp32 ONNX도 torch와 지표가 같다(argmax 500/500, max|Δp| 0.0001).
- **H10(int8 ≤ torch × 0.6, |ΔECE| ≤ 0.01, choice_accuracy 차 ≤ 0.01; 01:271은 "약 2배 빠름, argmax 일치 ≥ 99%"): 기각. 네 조건 모두 미달이다.**
  - 속도: int8은 torch보다 1.74배 느리다(0.6배 기준의 반대 방향).
  - ECE: +0.0154다.
  - 정확도: −0.012다.
  - argmax 일치: 0.930(35 flip), max|Δp| 0.646이다.
  - upstream fixture(torch 116.8 → onnx 66.3 → int8 46.3 ms, ece +0.006: docs/evals.md:102-104)와 속도 방향이 반대다.
- D7b에서 ORT를 intra 10 / inter 1로 고정해도 fp32는 457 ms, int8은 499 ms로 거의 그대로다. ORT 스레드 기본값 때문이 아니다. 가설은 torch CPU가 macOS Accelerate(AMX) fp32 GEMM을 쓰고 ORT MLAS는 그렇지 못하다는 것이다(미검증). 근거는 D1에서 M4 Pro CPU 10스레드의 1q가 upstream EPYC 4코어보다 2.4\~6.7배 빠르다는 점이다(state 길이가 달라 근사치).
- 함의: 이 머신과 비슷한 Apple silicon CPU 배포에서는 torch fp32가 ONNX보다 빠르고 정확하다. int8은 한국어 ynat에서 결정 7%를 바꾼다. 이는 export_onnx.py docstring과 맞는다(third_party/laya/scripts/export_onnx.py:20-29). docstring은 "INT8 is a size/latency option, not a free one. On CPU it is roughly 2x faster than eager"라고 쓰면서 "do not use it where the calibrated probability or confidence matters"라고 경고하고, multilingual의 per-tensor agreement를 83%로 적는다. 이 런의 agreement는 93%다. 반면 "2x faster" 주장은 M4 Pro에서 재현되지 않는다. x86 서버(ONNX 이득이 보고된 환경)에서는 별도 측정이 필요하다.
- D7 리포트는 지시된 명령대로 test 절반 255행을 포함한 500행을 채점했다. 정확도는 경로 간 비교용으로만 쓰고 Track B test 판정에는 쓰지 않는다(03 §3.2).

## 8. D8 메모리

**preload RSS.** `results/D/20261003-1307_rss_preload.{json,md}`. 디바이스마다 새 프로세스에서 `Router(models=로컬 경로, max_loaded=3)`를 만들고 multilingual → english → typed-decisions 순으로 `preload`했다. 단계마다 RSS를 재고, 상주 체크포인트마다 predict(short, 3q)를 1회 실행한 뒤 다시 쟀다.

| 상주 | CPU RSS GiB (predict 후) | 증분 | MPS RSS GiB | MPS current_allocated GiB | MPS driver_allocated GiB |
|---|---|---|---|---|---|
| 없음(import 후) | 0.191 | | 0.192 | 0.000 | 0.000 |
| multilingual | 2.066 (2.085) | +1.875 | 1.125 (1.249) | 1.207 | 1.243 |
| + english | 3.632 (3.666) | +1.566 | 1.707 (1.711) | 2.781 | 3.245 (3.253) |
| + typed-decisions | 5.230 (5.257) | +1.598 | 1.700 (1.702) | 4.355 | 5.253 |

- CPU 증분: english 1.57 GiB(1.68 GB), typed-decisions 1.60 GiB(1.72 GB)는 01:243 기대치(fp32 상주 약 1.7 GB)와 맞는다. multilingual 1.88 GiB(2.01 GB)는 기대치 "1.3 GB + tokenizer"보다 크다. 첫 로드에 torch·transformers 런타임 초기화가 함께 잡히고, 256k 어휘 tokenizer가 상주하기 때문이다. 세 개 상주는 5.23 GiB(5.6 GB)로 기대치 "약 5 GB + 활성화"와 일치한다.
- MPS에서는 가중치가 Metal 버퍼로 옮겨가 프로세스 RSS(1.1\~1.7 GiB)에 잡히지 않는다. 메모리 사이징은 RSS + `driver_allocated_memory`(세 개 상주 시 1.70 + 5.25 ≈ 7.0 GiB)로 봐야 한다.

**64-state `predict_batch` 중 peak RSS.** `results/D/20261003-1349_rss_peak_batch.{json,md}`. multilingual에 D4의 혼합 길이 64 states와 router_v1 질문을 쓴다. 모드마다 새 프로세스를 띄웠고, 로드 직후 RSS를 잰 다음 같은 호출을 두 번 하며 psutil로 10 ms마다 샘플링했다.

| device | 모드 | 로드 후 RSS GiB | call 1 peak RSS GiB | call 2 peak | peak − 로드 후 | MPS driver GiB (로드 후 → call 1 → call 2) |
|---|---|---|---|---|---|---|
| cpu | batch_size 16 | 2.054 | 4.480 | 4.485 | **+2.431** | |
| cpu | batch_size 16, sort_by_length | 2.070 | 3.925 | 3.926 | **+1.856** | |
| cpu | batch_size None (64개 한 forward) | 2.050 | 7.541 | 7.541 | **+5.491** | |
| mps | batch_size 16 | 1.110 | 1.245 | 1.245 | +0.135 | 1.243 → 2.287 → 2.287 |
| mps | batch_size 16, sort_by_length | 1.128 | 1.263 | 1.263 | +0.135 | 1.243 → 2.275 → 3.275 |
| mps | batch_size None | 1.112 | 1.247 | 1.248 | +0.136 | 1.243 → 4.383 → 4.383 |

- CPU 활성화 메모리는 길이 정렬로 24% 줄고(+2.43 → +1.86 GiB), 64개를 한 번에 넣으면 +5.5 GiB까지 오른다. 첫 호출에서 할당자가 커진 뒤 반납하지 않으므로 call 2의 peak가 call 1과 같다.
- MPS에서는 활성화가 Metal 버퍼에 잡혀 RSS 증가가 0.14 GiB뿐이고, driver 할당이 +1.0\~3.1 GiB 늘어난다.
- 앞선 런(`results/D/20261003-1329_rss_peak_batch.{json,md}`)은 warm-up 호출 뒤에 샘플링해서 delta가 약 0이었다. peak 값은 이번 런과 같다(cpu 4.481 / 3.909 / 7.539 GiB). 로드 후 기준선이 없어 보완 런으로 대체했다.
- 컨테이너 사이징(PoC, multilingual 1개, CPU): 상주 약 2.1 GiB에 64-state 배치 피크를 더하면 batch_size 16 + sort 기준 약 3.9 GiB다. upstream 전체 스크립트 peak 9.3 GiB(5회 로드, BENCHMARKS.md:286)와는 측정 대상이 다르다.

## 10. 문서 불일치 (docs는 수정하지 않음)

1. `docs/03_benchmark_plan.md:232`: Ryzen 6900HX 행이 "8스레드, HTTP 포함 | 329 ms p50"이다. upstream에서 329 ms는 inter-op 1 고정 **in-process 1질문**이고(third_party/laya/BENCHMARKS.md:249-255), HTTP 3질문 값은 783 ms다(BENCHMARKS.md:247). `docs/01_laya_analysis.md:223`은 올바르게 적었다.
2. `docs/03_benchmark_plan.md:249`: "multilingual은 34 MB tokenizer.json 파싱이 가중치 적용보다 비싸다". 측정 결과 multilingual `laya.load` 2.97\~3.13 s 중 tokenizer 재파싱이 0.92\~1.01 s였다. 가중치와 빌드가 약 2.0 s로 더 비싸다(D3).
3. `docs/03_benchmark_plan.md:74`, `docs/01_laya_analysis.md:240`: "shape마다 첫 호출에 최대 약 13초 Metal 커널 컴파일". M4 Pro와 torch 2.14.1에서 첫 호출 추가분은 약 0.1 s였다(D3 첫 0.12\~0.17 s vs 둘째 0.02\~0.08 s). 문서가 "최대"라고 했으니 틀린 것은 아니지만 기대치가 두 자릿수 크다.
4. `docs/03_benchmark_plan.md:262`: "MPS 배치 3\~4x". 측정은 MPS `predict_batch` vs loop 1.21\~1.25배(sorted), 0.59\~0.83배(unsorted)다(D4).
5. `docs/01_laya_analysis.md:270`(H9 "혼합 길이 한국어 64건")과 `docs/03_benchmark_plan.md:254-256`(n 64,256): 대상 크기가 다르다. 이 문서는 둘 다 측정했고 n=256을 주 근거로 썼다.
6. `docs/01_laya_analysis.md:271`과 `docs/03_benchmark_plan.md:298`: H10 수용 기준이 서로 다르다. 01은 "약 2배 빠르고 … argmax 일치 ≥ 99%", 03은 "int8 ≤ torch × 0.6, |ΔECE| ≤ 0.01, choice_accuracy 차 ≤ 0.01"이다. 이 문서는 둘 다 판정했고 둘 다 미달이다.
7. `docs/03_benchmark_plan.md:82`: "5문항 이상 또는 predict_batch는 fp16". autocast는 forward 한 번의 행 수(`input_ids.shape[0]`, laya/agent.py:1087)로 정해진다. 그래서 행이 5개 미만인 `predict_batch` 청크는 fp32로 돈다.
8. `docs/03_benchmark_plan.md:233-236`, `docs/01_laya_analysis.md:236-239`: M4 Pro 가설치가 측정과 어긋난다. CPU 1q는 multilingual 120\~250 / english 300\~600 ms라 했지만 측정은 37.7\~81.8 / 86.6\~204.5 ms다. CPU 10q/1q는 7\~10배라 했지만 3.2\~8.7배다. MPS 10q/1q는 2\~4배라 했지만 4.5\~9.1배다. 03:236이 "측정값으로 대체한다"고 했으므로 갱신이 필요하다.
9. `docs/00_README.md:106`, `docs/05_poc_plan.md:23`: "G7 통과"는 device parity를 근거로 했다(`results/go_no_go.json` G7 note에도 "G7 정의가 아닌 device parity 근거"라고 적혀 있음). D4로 정의대로 측정해 통과를 확인했다. G5·G6의 "대기"는 이제 측정값이 있다(통과).
10. `docs/03_benchmark_plan.md:266`: D5 검증 참조값 "reload CPU 7.4 s / T4 10.3 s"(README.md:542)에 측정 조건이 적혀 있지 않다. 로컬 경로와 프로세스 내 tokenizer 캐시 조건의 측정은 0.13 / 0.21 s로 조건이 다르다.
11. `docs/03_benchmark_plan.md:272`: D6 명령에 `LAYA_THREADS`가 없다. 이 런은 지시에 따라 MPS 서버에도 `LAYA_THREADS=10`을 줬다. `docs/00_README.md:101`과 `docs/03_benchmark_plan.md:281`의 G6는 body의 질문 수를 정하지 않았다. 판정은 지시대로 3-question body로 했다.
12. `docs/01_laya_analysis.md:243`: multilingual 상주 약 1.3 GB. 측정 증분은 1.88 GiB(2.0 GB)로, 첫 로드의 런타임 초기화와 tokenizer가 포함된 값이다(D8).
