# Track D performance summary (2026-10-03, Apple M4 Pro)

This document collects the D1\~D8 results of 03_benchmark_plan.md §6. The machine is an Apple M4 Pro (10P + 4E CPU, 20-core GPU/MPS, 48 GB), connected to AC power. The software is laya 0.3.23, torch 2.14.1, transformers 5.18.0, onnxruntime 1.30.0, Python 3.12.12, macOS 26.6.2 arm64, and the environment record is in `results/env/env_20261002-1333.json`. The three checkpoints are english / multilingual / typed-decisions, all from bundle snapshot `55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851` (realpath of the `models/*` symlinks (not included in the public repository), laya-serve `/health` revisions). The run card is `results/D/D_20261003.md`, the execution driver is `results/D/D_run.sh`, and the per-step load and verbatim command log is `results/D/logs/D_driver.log`.

Work started at 12:42; measurement ran 12:49:06 \~ 13:51:20 (about 62 min), and the total wall time including documentation was 12:42 \~ 14:00, about 1 h 18 min (within the 2.5 h cap). Latency is not compared directly with the upstream numbers because the hardware differs; the upstream values are listed alongside only as an order-of-magnitude reference (06 §1 writing rule).

**Deployment implications (PoC).**

- A single Korean inquiry with 1\~3 questions on multilingual takes 14\~23 ms in-process on MPS and 34\~57 ms on CPU. Even over HTTP, MPS 3q at 10 RPS has a p95 of 79 ms.
- The MPS advantage is only 2\~3x. With intermittent traffic, the idle penalty shrinks it further to 1.2\~2x (D1c, D6 open-loop).
- The server serializes inference. The throughput ceiling is 1 / service time: about 22 RPS for MPS 3q and about 10 RPS for CPU 3q.
- On CPU, mixed-length batches require `sort_by_length=True`. Batching without sorting is slower than the loop.
- On this machine, ONNX (fp32·int8) is slower than torch CPU, and int8 changes 7% of the decisions.

With an idle gap of 100 ms or more, MPS becomes 2.2\~3.6x slower and CPU 1.1\~2.3x slower. **Verdicts.**

- **G5 (3-question call p95 ≤ 100 ms MPS, ≤ 500 ms CPU 10 threads): passes for the PoC configuration (multilingual).** With back-to-back calls, the multilingual 3q p95 is CPU short 57.8 / long 247.8 ms and MPS short 22.6 / long 92.5 ms. With intermittent calls (D1c, short) it is also within the criterion: CPU 61.9\~100.5 ms, MPS 54.9\~90.6 ms. However, the p95 of 90.6 ms at an MPS gap of 1000 ms comes close to the criterion. english·typed-decisions pass on short (CPU 186.5 / 194.4, MPS 80.0 / 80.2) and fail on the 919-token long (CPU 529.5 / 1175.7, MPS 242.8 / 485.0).
- **H8 (MPS 1q 3\~6x faster than CPU, MPS sub-linear in the number of questions, CPU linear): rejected.**
  - The MPS 1q advantage is 2.33\~2.80x, below the lower end of the range.
  - MPS 10q/1q is 4.52\~9.05, closer to linear than the 01:239 expectation of 2\~4x.
  - CPU 10q/1q is sub-linear on short at 3.22\~5.69 and nearly linear on long at 7.29\~8.65.
  - As the number of questions grows, the CPU/MPS speed ratio stays constant at 1.9\~2.8x. On this machine, MPS does not absorb question batching any better than CPU.
  - upstream also reported EPYC CPU as linear (BENCHMARKS.md:286 "Batching questions saves little on CPU"). On M4 Pro CPU short, the question-batching gain is large (multilingual 37.7 → 121.4 ms, 3.2x for 10q).

CPU n=64 reaches up to 15% (b8 round 3 4.945 s vs median 4.302 s); these are short runs of around 4 seconds, so the noise is large. The H9 verdict therefore uses n=256 as the main evidence. padded slots is the sum of `input_ids.numel()` fed to the forward; the loop value is the actual token count. Batch parity is flip 0 against the same-device loop in every mode. MPS batches use fp16 autocast (rows = batch size ≥ 5), so max|Δp| is 0.0081\~0.0085. The MPS fp32 loop matches the CPU loop with flip 0, max|Δp| 0.0001. laya outputs probabilities with 4 decimal places, so 0.0001 is the floor of the measurement resolution.

- **G7 (predict vs predict_batch(sort_by_length=True), CPU): pass.** 0 argmax flips (64 + 256 states × bs 8/16/32), max|Δp| 0.0001 (the resolution floor) ≤ 0.01. The earlier "pass" in 05 §1 (docs/05_poc_plan.md:23) and 00 §6 (docs/00_README.md:106) rested on device parity (results/go_no_go.json G7 note). This run is the first evidence measured per the G7 definition.
- **H9 (mixed-length Korean, sort_by_length ≥ 1.3x on CPU, flip 0, max|Δp| ≤ 0.01): supported.**
  - Against unsorted at the same batch size: 1.67x (bs 8), 1.83x (bs 16) and 2.08x (bs 32) at n=256, and 1.46\~1.56x at n=64.
  - Against the loop as well, n=256 b8s 1.39x and b16s 1.42x exceed 1.3x. However, n=64 b16s 1.27x and b32s 0.93x do not.
  - This is in the same range as upstream's 1.42x (README.md:277, CLI, 128 cases, batch 8) and 2.15x (research/README.md:69, 10,000 cases).
- **Design implications.**
  - On CPU, an unsorted `predict_batch` is slower than the loop (0.62\~0.93x), because with Korean states of widely varying length, padding inflates the slots 1.6\~2.2x. For CPU batches, `sort_by_length=True` is effectively mandatory.
  - On MPS, even sorted batches reach only 1.21\~1.25x of the loop, far short of the 03:262 expectation "MPS batching 3\~4x" (decide_batch on 8 cases, 3.6x, README.md:998-1000). On the M4 Pro, MPS throughput barely increases with more rows (consistent with the D1 H8 result).

- **G6 (p95 ≤ 150 ms at 10 RPS on `laya-serve`, MPS, preload, 3-question body): pass.** p95 79.4 ms (p50 63.5, p99 85.1, max 129.0), and errors and 503s are 0. The 1q body has a p95 of 57.3 ms. The CPU server under the same conditions is also within the criterion at p95 135.8 ms, but its 3q service time is about 98 ms, so its utilization at 10 RPS is about 100%. There is no headroom.
- **Inference is serialized in the server.** This is due to `ThreadPoolExecutor(max_workers=1)` (laya/serve.py:701) and the `asyncio.Lock` gate (serve.py:863-867; for batch, 969-971). Regardless of concurrency, closed-loop throughput saturates at about 50 RPS for MPS 1q, about 22.6 RPS for 3q, 19.7 RPS for CPU 1q and 10.0 RPS for 3q. Latency grows in proportion to concurrency (MPS 3q c=8: 353 ms). The capacity of a single-process server is 1 / service time.
- **503 and Retry-After:** there were 0 503s in every mode, because concurrency 8 and 20 RPS (a queue of at most a few requests) did not exceed the `LAYA_MAX_CONCURRENT` default of 16 (serve.py:78). The Retry-After compliance logic (the client waits for the header value) was implemented but never executed. Verifying the 503 path needs an overload run with concurrency 17 or more or MPS 3q at 23 RPS or more (not run).
- **Intermittent-traffic penalty (the same phenomenon as D1c).** The server-side inference p50 of the MPS open-loop is 46.7 → 41.7 → 26.7 ms (1q) at 5 → 10 → 20 RPS, larger than the 19.4 ms of back-to-back requests (closed c=1); the shorter the request interval, the faster it gets. 3q likewise goes 69.8 → 57.3 → 44.9 ms. The CPU server on the same machine shows almost none of this penalty at 10 RPS (50.5 vs 49.5 ms), because its interval of about 50 ms is shorter than the 200 ms at which the CPU penalty grew in D1c.
- The HTTP overhead (client p50 − server infer p50) is about 1 ms for back-to-back requests and 1\~7 ms in open-loop, largest for MPS at low load (5\~10 RPS). The fixed overhead of about 93 ms on upstream's GB10 (BENCHMARKS.md:239) does not reproduce here.
- `/v1/systemone/batch` (MPS, 1q, `batch_size` unspecified, so one forward): 16 states 218 ms (73.5 states/s), 64 states 848.5 ms (75.4 states/s). That is about 1.5x the throughput of back-to-back single requests (48.4 RPS).

A separate measurement is needed on an x86 server (the environment where the ONNX gain was reported).
