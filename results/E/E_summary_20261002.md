## Decisions and assumptions

- **payload = the official map of the pooled fit.** The rule fixed before seeing the results was "per-task domain_8, but pooled if pooled lowers the domain_8 test ECE by more than 0.02". The measurement was 0.123 → 0.098, a difference of 0.025. There is also dev evidence in the same direction: domain_8 dev ECE is 0.078 per-task (in-sample) and 0.050 pooled, and pooled has twice the fit sample (495). On NLL, per-task is marginally better (1.372 vs 1.377). And the G3 verdict hinges on this choice (0.098 passes, 0.123 fails). This fact is kept as is in reading 5 and in E5.
- **payload form = type scalar.** `temperature[choice] = 1.9161`, following the "type-level temperature (1 value for choice)" of 05 P3. This value applies to every choice question of the same agent (including k=2, 3-5, 11+), but those buckets were not validated. The alternative is the bucket-restricted form `{"temperature": [1,1,1], "temperature_by_options": {"choice:6-10": 1.9161}}`. On router_v1 (k=8) both forms give the same output; they differ only for the arbitrary-question examples of the P2-UI. This is an item to choose in the ADR.
- The gate T is compared against the `answer_confidence` that the API returns (max p, rounded to 4 decimals). It is the same float32 computation as `_decode_answers`, so it matched bit for bit in E4.
- The T grid was interpreted as {0.50, 0.55, …, 0.95} ∪ {0.99}. The T for each error budget is "the confidence at the maximum-coverage point that satisfies the budget" in metrics_extra `coverage_table` (tied confidences are not split). It is chosen on dev and then applied to test as `p >= T`.
- Selection rule for the per-domain T: for each predicted domain, pick the maximum-coverage T whose routed error in that domain is at most the budget. If no such T exists, None, i.e., always FALLBACK. So the overall dev error is always within the budget. No optimization that splits the overall budget across domains (Lagrangian) was done, because with small samples it would push toward even more overfitting.
- E6 was computed from the p(true) values of the B report (rounded to 4 decimals). Neither dev nor test has a row with p = 0, and there are 182 distinct values.

In short, calibration cannot move the frontier (maximum coverage per error budget). The ±0.01 \~ 0.03 changes are the effect of 2 \~ 4% of the ranking being shuffled, and their direction differs by set. What changes is the scale of T, the ECE and the top resolution. The ways to raise coverage are accuracy (P4 fine-tuning, wording) or a policy that changes the ranking (per-domain T). The per-domain T failed test validation at this sample size.

The dev half of the 2,917-row pool is about 1,460 rows, and even adding the 245 ynat dev rows stays below 2,000. `compute_ece=True` holds out 20% only when the fit side has 2,000 or more (laya/calibrate.py:178). 6. `docs/03_benchmark_plan.md:466`, `docs/05_poc_plan.md:470`: calling `records_from_labeled(agent, pairs)` as is with a real Agent raises `RuntimeError: Can't call numpy() on Tensor that requires grad`. laya/calibrate.py:286 calls `agent._forward`, and laya/agent.py:1177 calls `.numpy()` on a tensor that tracks grad. `predict_batch` carries `@torch.no_grad()` (agent.py:1248), but this function does not. A different spelling of the path alone raises the warning, while different weights at the same path·config raise none.
8. `docs/00_README.md:97` (G2): not a defect but a note on coupling. Since coverage@5% ≤ acc/0.95, G2 cannot pass by definition if the G1 accuracy is below 0.665. G2 must not be read as a criterion independent of G1.
